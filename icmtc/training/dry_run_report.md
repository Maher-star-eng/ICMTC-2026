# Dry Run Report: First Full-Pipeline Integration Test (Mac, Zero Hardware)

**ICMTC 2026, Mission 2** — `capture -> Mission -> detector -> tracker -> MedianGeolocatorAdapter -> VisionSystem -> judge log`

Generated by `training/dry_run.py` (`python -m training.dry_run`). Raw captured
stdout: `training/dry_run_raw_log.txt`. Judge logs:
`training/dry_run_judge_log.json` (primary), `training/dry_run_judge_log_secondary.json`
(secondary). Synthetic footage: `training/dry_run_footage/frame_00.png` … `frame_09.png`.

> **What this run proves, and what it does not.** Every module below has
> already been unit-tested in isolation with fakes. This is the first time
> real instances of all of them have ever been wired together and run as one
> system. The purpose is to prove the **wiring** is correct — that real
> objects pass real data to each other without a seam breaking — **not** to
> re-validate detection accuracy, which is already measured rigorously
> against the held-out validation set in `masked_validation_report.md`,
> `threshold_sweep_report.md`, and `resolution_and_remap_report.md`. Nothing
> in this document should be read as a detection-accuracy result.

**Independent re-execution.** This report reflects a live re-run of
`training.dry_run` executed directly in this session (not a stale copy of an
earlier session's numbers). The full unit test suite (`pytest tests/`, 288
tests) was also run immediately beforehand and passed clean, including the
three tests covering `Mission.__init__`'s soft `detector.target_class_ids`
vs. `briefed_target_class_ids` mismatch check (`tests/test_mission.py`,
around `test_mismatched_target_class_ids_warns` /
`test_matching_target_class_ids_does_not_warn` /
`test_detector_without_target_class_ids_does_not_warn`) — this defensive
check (`core/mission.py`, `Mission.__init__`, getattr-based, warn-only,
never raises) was already present in the codebase and did not need to be
added. Exact `process_frame` call counts below differ slightly from a prior
run of this same script (266 vs. 234 primary calls, 2320 vs. 2346 secondary
calls) purely because of real-time scheduling jitter in
`LatestFrameQueue`'s reprocessing behavior (§7) — every qualitative finding
(masking, median aggregation, fault tolerance, state machine legality, judge
log validity) reproduces identically.

### Telemetry — **synthetic**

No MAVLink flight exists to record from. `training/dry_run.py`'s
`SyntheticTelemetry` class fabricates a slow-nadir-pass `Pose` sequence.
Every value is documented in its docstring and reproduced here:

| Field | Value | Note |
|---|---|---|

Camera intrinsics used for `MedianGeolocatorAdapter` (also synthetic,
arbitrary, chosen only to be plausible for a 640×480 frame — **no real
camera was ever calibrated for this run**): `fx=fy=600`, `cx=320`, `cy=240`.

Two independently-configurable fault windows were built into
`SyntheticTelemetry` and used for the required fault injection (§4):

- **Telemetry gap** (`pose_at()` returns `None`): elapsed 1.8–2.7 s since the
  first call.
- **Single bad-gimbal frame** (secondary check only): elapsed 3.3–3.6 s,
  gimbal pitch pinned to −1° instead of −90° — verified empirically via

  the historical "~2 km bug" this project's `MedianGeolocatorAdapter` exists
  to fix (see `core/mission.py` module header, "THE FIX").

### Two runs, and why there are two

The **primary run** uses the real trained model. As anticipated, it produced
**zero detections** on the synthetic schematic footage (confirmed
empirically, independently, in this session: max raw class-score across all
anchors × 196 classes on this exact tricolor frame, `frame_04.png`, was
0.0064, nowhere near any threshold — see raw diagnostic below). With zero
detections, there is no confirmed track to observe the tracker/median-adapter

`Tracker`, `MedianGeolocatorAdapter`, `VisionSystem`, and `Mission` classes,
with only the detector's model backend swapped from `NcnnBackend` to
`vision.detector.StubBackend` (an existing, first-class backend in this
codebase, used throughout its own test suite) scripted to emit one
drifting-box detection of the briefed target class per frame. **This does
not stand in for "real Detector"** anywhere in the required checks; it
exists solely to give checks 2 and 4 something to observe.

  (`model.ncnn.param`/`.bin` + `metadata.yaml`), loaded via the real
  `vision.detector.Detector` + `NcnnBackend` (the actual Pi-deployment

  `metadata.yaml` — `resolve_class_ids_by_name(class_names, ("Egypt",
  "Iraq", "Syria", "Yemen"))` → `{50, 78, 170, 193}`. No numeric id is
  hardcoded anywhere in the script; `target_flag_class=50` (Egypt) is

  immediately after `build_detector(...)`, mirroring exactly how
  `core/mission.py`'s `main()` now wires it.

  `Mission.__init__` compares `detector.target_class_ids` against

  run the two sets are identical by construction (`{50, 78, 170, 193}` both
  times), so the warning correctly stayed silent — confirmed by grepping
  `training/dry_run_raw_log.txt` for `"does not match briefed"` (zero
  matches). The mismatch path itself is covered separately by three unit
  tests in `tests/test_mission.py`, not re-tested here (this dry run does
  not deliberately wire a mismatched detector — see Guardrails).
- **Config**: built via `core.config.from_dicts` (no YAML files on disk needed):
  `search_altitude_m=55.0`, `ground_speed_mps=5.0`, `iou_threshold=0.3`,
  `min_hits=2`, `max_age=5`, `lane_overlap=0.2`, `gimbal_reference_frame="body"`.
- **Capture**: real `vision.capture.FileFrameSource` (image-directory mode)
  + real `LatestFrameQueue`, `realtime=True`, `fps=2.0` (deliberately slow —
  see the reprocessing-rate observation below for why).
- **Judge log**: real `ioutils.output.write_judge_log`, invoked via the real
  `Mission`'s `judge_log_path=` at handoff — never called directly by the script.

## 3. Log summary: state transitions, detections, coordinate evolution

### Primary run (real ncnn model)

```
[PRIMARY] initial state: SEARCHING (frame_idx=0)
[PRIMARY] frame_idx=266: SEARCHING -> HANDOFF_COMPLETE
[PRIMARY] acknowledge_handoff() -> DONE
```

266 `process_frame` calls were made in 4.516 s (58.90 calls/s) against only
**10 source images** — see the reprocessing-rate observation below for why.
Zero detections were logged across all 266 calls
(`all_class_ids_seen=[]`), so there is no coordinate history to report for
this run — no track was ever confirmed. State went directly
SEARCHING → HANDOFF_COMPLETE (COVERAGE_COMPLETE is a same-step
pass-through in `Mission._maybe_handoff`, never independently observable
between two `step()` calls — this is expected, not a skipped state).

### Secondary run (stub detector, wiring-only)

```
[SECONDARY] initial state: SEARCHING (frame_idx=0)
[SECONDARY] frame_idx=2: SEARCHING -> TRACKING
[SECONDARY] frame_idx=2320: TRACKING -> HANDOFF_COMPLETE
[SECONDARY] acknowledge_handoff() -> DONE
```

SEARCHING held only through the first `step()` (frame_idx 0→1); by
frame_idx=2 (`min_hits=2` satisfied on the second `process_frame` call) the
track was confirmed and the state moved to TRACKING, correctly preceding
TARGET_FOUND in the final result. It never entered an autonomy-owned state
(TARGETING/DROPPING/RETURNING do not exist in `MissionState` at all — see
`core/mission.py` `MissionState`/`_LEGAL_TRANSITIONS`).

**Coordinate evolution** (per-call evidence, `LoggingGeolocatorWrapper`
peeking `MedianGeolocatorAdapter._history` immediately after each real
`.locate()` call):

- `MedianGeolocatorAdapter`'s history is bounded to 5 samples
  (`history_window` default), confirmed by every logged call reporting
  `history_len=5` once warmed up — matches `core/mission.py` ASSUMPTION MS1
  exactly.
- **4 calls** were logged where the single-frame estimate diverged from the
  median returned that same call by **>50 m** (all four ≈**1086 m**,
  matching the ≈1.08 km predicted for the −1° gimbal glitch):

  ```
  single_frame_coord=(30.009738879206612, 31.00074897842395)
  median_coord      =(30.000000018756793, 31.00003803362089)
  single_vs_median_m=1086.2939072079048
  ```

  This is direct, in-the-moment evidence that **at the instant the bad
  frame entered the window, the adapter did not report it** — it reported
  the median of the other 4 (good) samples plus the bad one, which stayed
  within centimetres of the good cluster. This is the ~2 km bug's
  regression check, reproduced at the system level, not just in
  `MedianGeolocatorAdapter`'s own unit test.
- The **final** reported history (5 entries, all within millimetres of each
  other) no longer contains the glitched sample — by the time the run ended,
  thousands of further same-slot re-evaluations (see below) had aged it out
  of the bounded window:
  ```
  {1: [(30.000006000967417, 31.000038033623184),
       (30.000006011295543, 31.000038033623188),
       (30.000006021886996, 31.00003803362319),
       (30.00000603198283,  31.000038033623195),
       (30.000006041934498, 31.0000380336232)]}
  ```
  The *final* `MissionResult.target_coord`
  (`30.000006021886996, 31.00003803362319`) is therefore not itself
  "resisting an outlier at the end" — the **in-the-moment evidence above**
  is what proves resistance; see the Observations section for why the final
  snapshot alone would have been misleading.

## 4. Fault injection result (required check 5)

**Mechanism**: `SyntheticTelemetry.pose_at()` returns `None` for a fixed
elapsed-time window (1.8–2.7 s after the first call), simulating a real
telemetry dropout — exactly the mechanism the task specified.

**Primary run**: 61 consecutive `pose_at()` calls (call indices 98–158 of
266) returned `None`. **No crash.** `mission.degraded_count == 0` (see
"Observations" — this run never had a confirmed track for `None` telemetry
to have any visible effect on).

**Secondary run**: 512 consecutive calls (call indices 912–1423 of 2320)
returned `None`, squarely mid-run. **No crash.** `mission.degraded_count == 0`.

**Observed behavior matches `output.py` ASSUMPTION O5 (last-known-coord
fallback), not O2 (DEGRADED)** — and this is the *correct*, documented
behavior, not a miss: `pose_at()` returning `None` is normal, handled input
(`if pose is not None: ...`) inside `VisionSystem.process_frame`'s `try`
block, not an exception. `MissionResult.status` is DEGRADED only when
`process_frame` itself raises (covered separately by existing unit tests —
`tests/test_mission.py::test_degraded_frames_do_not_crash_the_loop_and_recover`,
`tests/test_output.py`). During the gap, the confirmed track (secondary run)
kept reporting its last successfully-geolocated coordinate
(`ioutils/output.py` `_last_known_coord` cache) rather than vanishing from
`all_flags`; state stayed TRACKING throughout, never regressing. **Normal
operation resumed immediately once the gap window closed** — the very next
non-gap `pose_at()` call produced a fresh geolocation and the history
continued growing normally. The secondary run also carried a second,
independent fault window (a single glitched-gimbal reading, elapsed
3.3–3.6 s, 148 consecutive `pose_at()` calls, indices 1725–1872) — this is
the outlier the median-aggregation evidence in §3 comes from; it too caused
no crash and no state regression, only a temporarily-outvoted geolocation
sample.

## 7. Observation: `LatestFrameQueue` reprocesses the same frame many times

**Not one of the 7 requested checks, but a genuine, unmodified discovery
from real objects talking to each other for the first time**, and worth
recording plainly rather than glossing over.

`vision/capture.py`'s `LatestFrameQueue.read()` never clears its single slot
after being read (by design — CAP8: "each new frame ... overwrites the
previous one"). `core/mission.py`'s `Mission.step()` calls
`frame_queue.read()` on every iteration and, once at least one frame has
ever arrived, `read()` never again returns `None` — so `Mission.step()`
never sleeps again (the `time.sleep(_FRAME_POLL_INTERVAL_S)` branch only
fires while `item is None`, which is only true before the very first frame).
The result: between two real frame arrivals (0.5 s apart at this run's
`fps=2.0`), `Mission.step()` spins as fast as the detector/tracker/geolocator
chain allows, reprocessing the **exact same frame object** repeatedly.

Measured directly (primary run, `id(frame)` tracked per `detect()` call):
**266 `detect()` calls resolved to only 9 distinct frame objects** — i.e.
each distinct frame served by `LatestFrameQueue` was, on average, processed
roughly **30 times** before the next one arrived (fewer than 10 distinct
objects seen because the very fast final frames can arrive before
`LatestFrameQueue`'s background thread and the main loop's very first
iterations have fully synced — not investigated further here, out of scope
for this dry run). The secondary run's much faster stub detector reprocessed
the same slot even harder: 2320 calls for the same 10 images. **Both figures
differ from a prior run of this exact, unmodified script** (234/8 and 2346
calls respectively) purely because of real-time scheduling jitter — this
variability is itself expected and consistent with the mechanism described
here, not a sign of nondeterministic logic elsewhere in the pipeline (the
qualitative behavior — masking, median aggregation, fault handling, state
transitions, judge log validity — was identical across both runs).

This is not presented as a bug to fix in this task (per the guardrail:
report, don't silently modify production code to make the run look
different) — `LatestFrameQueue`'s "always serve the newest frame, never
queue stale ones" design is explicitly intentional for a live feed. But it
is a real, previously-unobserved characteristic of the assembled system
worth flagging for whoever owns capture.py/mission.py next: on hardware
where a real detector's inference time is much shorter than the frame
interval, `Mission.step()`'s busy loop will spin at a rate bounded only by
CPU speed, doing repeated, wasted work on stale frames between real
captures. It also explains why `frame_idx` in `MissionResult`/logs does not
correspond 1:1 with source images, which is worth knowing when reading
production logs. It is why the `_DriftingFlagScript`'s per-call box drift
had to be capped (20 calls' worth) rather than left unbounded, and why the
in-the-moment outlier-evidence logging (§3) was necessary — the naive "check
the final history" design this dry run started with would have silently
missed the glitch (already aged out by run end), which is itself a useful
lesson about how to correctly instrument this system for future dry runs.

## Closing statement: what this run does and does not prove

**This run proves**: a real trained model loaded through the real ncnn
deployment backend, real masking configured by name (never a hardcoded id),
a real `Tracker`, a real `MedianGeolocatorAdapter`, a real `VisionSystem`,
and the real `Mission` state machine can be constructed together and driven
end-to-end by a real `FileFrameSource`/`LatestFrameQueue` without any seam
breaking — no exception escaped, the state machine only ever took legal
transitions, a telemetry dropout degraded gracefully per the documented
contract, the median-aggregation fix demonstrably resists a kilometre-scale
single-frame outlier in real time (not just in `MedianGeolocatorAdapter`'s
own unit test), and a real judge log was written and is valid. It also
surfaced one genuine, previously-unobserved wiring characteristic
(§7 — `LatestFrameQueue` frame reprocessing) worth a follow-up look, and it
was independently reproduced end-to-end in this session with the same
qualitative outcome as a prior run.

**This run does not prove**: that the trained model detects real flags in
real footage. The synthetic schematic frames used here are explicitly
PLUMBING ONLY, and the real-model half of this run (correctly, as
predicted) found nothing in them. Detection accuracy is, and remains,
whatever `masked_validation_report.md` / `threshold_sweep_report.md` /
`resolution_and_remap_report.md` already measured against the held-out
validation set — this document adds nothing to and subtracts nothing from
those numbers. **A short real recording of a physical flag (even an
informal phone/webcam clip) is still needed before any run of this harness
can also serve as a live detection-accuracy dry run**, in addition to the
integration/wiring proof above.
